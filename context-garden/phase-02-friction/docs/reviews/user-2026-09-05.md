# user review of context-garden/phase-02-friction

**Persona:** user · **Score:** 7/10 · 2026-09-05T02:51:01+00:00

The loop now runs end to end and, more importantly, stops well: when a worker fails or refuses, the Inbox tells me exactly what happened and what each button does, and cost, transcripts and a digest are one click away. What still undermines trust is the human interface at the edges: I am notified to triage before the automated review has a verdict (three pings for one task), the notification hook is undocumented in this repo and fails silently, and a fresh init defaults to ten parallel workers with no budget. Fix the ping timing and the docs gaps and I would run this on real work without watching it.

## High

- **notifications** — The triage card and notify hook fire the instant a draft PR opens, before the automated review has spoken, so one task produced three awaiting_triage pings of which the first two were wasted.
  - suggestion: Hold the triage notification (and ideally the Inbox card) until the automated review round for that push has a verdict, or notify once per PR per review outcome.
- **notifications** — notify.command is documented nowhere in this repo (README and docs have zero mentions) and notify() swallows every error, so a misconfigured hook is invisible.
  - suggestion: Document the notify block with an example in README and examples/garden.work.yaml; have doctor run the command once with a test payload; log a hook failure to the task or scheduler log instead of passing silently.

## Medium

- **defaults** — garden init writes max_parallel: 10, budgets: {} and review on, so a first real serve can start ten paid sessions with no cap.
  - suggestion: Default init to max_parallel 2 or 3 and a commented budget example; have doctor warn when no budget is set for any phase.
- **retro** — garden retro on a fresh garden reports a missing self product and plans six persona runs at unknown cost; the self: true key is not in the README.
  - suggestion: Document self products in README and have retro's dry-run print the exact YAML needed; let --personas pick a subset.
- **triage** — If marking the PR ready on GitHub fails, the failure is only logged and the next poll reverts the task with the misleading note 'converted back to draft on GitHub' and pings again.
  - suggestion: When mark_ready fails, keep the task in awaiting_triage with the error on the card rather than transitioning and reverting.

## Low

- **cli** — garden status is unreadable at 80 columns; every column header truncates to two letters.
  - suggestion: Drop or merge the rarely non-zero columns at narrow widths, or print a per-phase line format when the terminal is under about 120 columns.
- **friction** — garden friction writes a 'None.' section for every PR whose friction was empty, so the planning document is mostly noise.
  - suggestion: Skip entries whose friction is empty or 'None' and list them in one summary line.
- **cli** — About sixty top-level commands with no grouping make garden --help a wall for a new user.
  - suggestion: Group commands in help (setup, run the loop, decide, inspect, phase wrap-up) or move rare ones under subcommands.
- **live output** — Live transcript needs output_format: stream-json, which the README does not mention; the task page just says 'no output yet'.
  - suggestion: Document the key next to the harness config and, when a run is active but the format is claude-json, say on the task page how to turn live output on.
