# security review of context-garden/phase-10

**Persona:** security · **Score:** 7/10 · 2026-09-13T23:54:06+00:00

Phase 10 establishes credible ownership and handoff protections for the accepted trusted-team Git architecture, with particularly valuable safeguards around unresolved execution and isolated public publication. I found one medium-severity browser boundary gap: automatic local authentication accepts private reads under an unrecognized Host. I reproduced that middleware behavior with synthetic data; I did not demonstrate browser exploitation or rerun the full suite. The walkthrough was permission-denied, and supplied release evidence explicitly says production multiplayer remains unactivated.

## Reaction

I come away from Phase 10 with more confidence in its ownership model than in the browser boundary around that model. The difficult security problem here is making an ownership change mean something while an older worker may still be running or an external operation may already have happened. Reading the final Git protocol and implementation, I see a deliberate preference for preserving uncertainty and waiting. That is the tradeoff I would choose for a small team running autonomous development with real publication and spending authority.

The most persuasive moment in the supplied evidence is the sequence of CG-631 fixes. The author finals describe preventing permit deletion, then preserving the complete admitted claim identity so a replacement claim cannot orphan unresolved work. Those are substantive security corrections. An apparently tidy state transition could otherwise erase the very record that prevents a second installation from acting. In the current code, I found explicit protections against changing admitted claim identities, deleting effect recovery evidence, and manufacturing permit status through generic updates. The corresponding tests inspect sequential and atomic bypass attempts. I value that specificity much more than a broad statement that reassignment is safe.

CG-634 also illustrates why I would distinguish review friction carefully. Its supplied author final says a permit lifecycle guard was lost during rebase and restored. Recovering that guard warranted attention because the resulting behavior mattered. A changed SHA by itself would not. Likewise, the accepted CG-690 denial of a browser principal attempting a phase mutation through another installation is consistent with the installation-bound execution contract. I would retain that protection and its accepted 403 expectation. Making the expected redirect prettier would provide no security benefit.

I accept the owner's decision to use Git rather than maintain a separate authoritative service. The contract states the crucial limitation plainly: repository writers are trusted protocol participants, and project filters do not provide confidentiality against someone who can read the repository. The implementation's explicit expected-predecessor push, single-parent history checks, and operation fingerprints support coordination within that boundary. They do not turn Git permissions into per-task access control, and the supplied design does not pretend otherwise. I would preserve this honest limitation rather than introduce a hidden service to satisfy a stronger threat model the owner did not select.

The public viewer is another decision I find reassuring. Reading publication.py and web/public.py, I see a separately constructed application that consumes a small projection rather than carrying the live scheduler and private store behind hidden controls. Publication defaults to empty, field names are allowlisted, free-form content requires an explicit selection, and rendered values are escaped. Tests cover denied routes and replacement of a published snapshot. This makes accidental exposure easier to reason about. Explicitly publishing prose still requires judgment about its contents; an allowlisted field is not evidence that every sentence in it is suitable for public retention.

Automatic local identity is where my assessment becomes less comfortable. I support removing repetitive login and identifier entry from the owner's normal workflow. However, the production middleware grants the local principal to requests without a bearer token before establishing that the request addressed an approved server hostname. Its Origin protection applies to mutations. I exercised that middleware entirely in memory with synthetic content: a GET under an attacker-style hostname returned the local principal and private response, while the corresponding cross-origin POST was denied. That difference matters because confidentiality is a separate boundary from permission to change state.

I have not demonstrated an end-to-end DNS-rebinding attack in a browser, and browser network restrictions can affect exploitability. Nevertheless, the application should reject unrecognized hosts itself before lending a request its ambient local identity. A small explicit Host allowlist can close this gap while preserving automatic startup. I would prioritize that focused fix before activating multiplayer, without adding another ordinary-user login ceremony or reopening the accepted ownership design.

My confidence also has clear evidence limits. The supplied walkthrough directory returned permission denied, so I cannot quote its pages or claim to have inspected their presentation. The phase evidence says that capture represents the older running build and that 0.4.3 passed isolated release checks without production multiplayer cutover. I treated those as supplied observations, separately from my own source inspection and middleware reproduction. I did not rerun the full suite, modify files, or commit. For the next step, I would retain the existing handoff regressions, fix the browser read boundary, and make the already-requested retrospective evidence readable through the existing follow-up. This phase needs a few precise corrections and an honest deployment boundary, not another broad procedural review cycle.

## Medium

- **Automatic local session / HTTP Host validation** — Automatic local authentication grants private read access under arbitrary Host headers, leaving a DNS-rebinding confidentiality gap.
  - suggestion: In src/garden/web/app.py and src/garden/web/trust.py, validate the request Host against explicitly configured listener names before granting the automatic local principal, covering GET and HEAD as well as mutations. An attacker-controlled page could rebind its hostname to the local listener and read member-visible tasks or logs where browser network protections permit; the existing POST Origin check does not protect these reads. An in-memory reproduction using the production OriginCheck returned 200 and the synthetic local principal for an unrecognized Host without credentials, while the cross-origin POST returned 403. Add a focused regression proving unknown hosts are rejected and permitted localhost names retain automatic startup; do not derive the allowlist from request or forwarded headers.
