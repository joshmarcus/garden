# staff-engineer review of context-garden/phase-10

**Persona:** staff-engineer · **Score:** 6/10 · 2026-09-13T23:54:06+00:00

Phase 10 delivers substantial ownership and handoff safeguards, with useful real-Git regressions and simpler interaction contracts. However, the supported migration/reversal path still targets the rejected coordinator architecture, Git transport has no execution deadlines, and refresh cost grows with all retained history. These deserve focused follow-ups before production multiplayer activation. This was a read-only source and supplied-evidence review: I changed no files, ran no tests, and could not access the walkthrough directory.

## Reaction

I would welcome several of this phase’s decisions as its future maintainer. The distinction between a person, an installation, and an execution claim is necessary, and the final design treats it seriously. Two installations belonging to one person still contend. A browser credential does not turn someone else’s running server into my execution authority. Pending ownership is distinct from effective ownership. These are boundaries I want established before multiplayer becomes routine, because reconstructing them after users accumulate work would be much harder.

The Git architecture is an accepted owner decision, and I would work within it. A dedicated state ref with exact-predecessor transactions is understandable, inspectable infrastructure. I particularly value the explicit refusal to infer that an absent owner has stopped executing. Git cannot kill a partitioned process, and pretending otherwise would make the product easier to demonstrate but harder to trust. Preserving an unresolved obligation until acknowledgement or external fencing is the right tradeoff, even when it leaves a handoff waiting for a person.

Reading the actual author and reviewer finals changed how I interpreted the revision counts. The CG-631 changes were not simply repeated demands for differently formatted evidence. Preventing permit deletion was substantive; subsequently preventing claim-identity replacement closed another route around the same safety boundary. The CG-634 final also records a permit guard lost during rebase. Those deserve behavioural regressions. Conversely, the accepted CG-690 denial through another user’s installation is correct: changing that response to a redirect would weaken the intended boundary. I would not turn that accepted correction, a mechanical SHA change, or an unmapped criterion label into another implementation round. The existing CG-661 and CG-682 drafts are appropriate places to improve that distinction.

My confidence drops at the migration boundary. Reading the code, I found that the normal client rejects the old coordinator URL, while migration preview requires it. Commit still initializes SQLite authority. More concerning, standalone export checks local runs and the old coordinator database, then produces an archive configured for standalone use; it does not inspect the accepted Git obligations held elsewhere. This is more than stale terminology. Recovery commands are where an operator should be able to rely on the architecture most strongly. I would prioritize a coherent Git migration and reversal path over further convenience features, with tests proving both refusal during uncertain work and successful progress after acknowledged quiescence.

I also worry about the ordinary experience of a remote becoming slow rather than cleanly unavailable. The transport subprocesses have no deadlines. That means the careful stale-state and recovery logic only helps after Git returns. A hung fetch, push, or credential helper can prevent that logic from being reached. As the maintainer trying to understand an apparently frozen scheduler, I would want one bounded transport boundary, an operation identifier, and a clear distinction between failure before publication and an unknown publication result. This does not require a coordinator service; it requires making the chosen transport operationally complete.

History handling is the other deferred cost I would address early. Every refresh validates every commit from the root, with several subprocesses and a state decode per commit. Each transaction also carries the accumulated operation records. I have not measured production latency, so I am not claiming an observed performance incident. The source nevertheless makes retained history part of every current authority check. I would cache validated immutable ancestry and batch object reads before introducing sharding or changing the protocol. That keeps the auditability I like while avoiding an increasingly expensive explanation for why an otherwise idle garden is slow.

The tests provide real reassurance at the protocol level: independent clones, competing processes, ambiguous acknowledgements, immutable identities, and positive terminal handoff paths are present. But the prominent integrated two-user and phase-owner journeys still construct the HTTP/SQLite coordinator and inject its client. That leaves future maintainers with two competing pictures of the architecture. I would port those journeys through normal Git configuration and retain legacy tests only where compatibility has an explicit purpose. Passing tests should teach the next engineer how the supported product actually starts and recovers.

I appreciate the later simplifications: inherited phase ownership, concurrency-only operating profiles, one assignment interaction, and shared actionable-attention logic reduce concepts the operator must manage. I cannot independently judge their visual outcome. The walkthrough directory was permission-denied, and the supplied evidence says it represents the older operator build anyway. The supplied release checks are useful evidence, but they are not production multiplayer experience or checks I personally reran. My next tradeoff would be to preserve phase closure and route these concrete issues into frozen follow-up proposals for owner disposition, while resolving migration and bounded recovery before activating multiplayer in production.

## High

- **Migration and recovery** — Migration still initializes SQLite authority, and standalone export does not check accepted Git claims or unresolved effects.
  - suggestion: Replace the coordinator-dependent preview/commit/export paths in src/garden/migration.py:131-173,218-225,257-266 with the accepted Git protocol. Normal enrollment clears coordinator_url, while preview requires it and startup rejects it. Make reversal require authoritative Git quiescence and preserve unresolved obligations. Add CLI-boundary tests for Git-only migration, interrupted commit recovery, and refusal to export while another installation retains a pending permit.
- **Git transport deadlines** — Git coordination subprocesses have no timeout, so a stalled remote or credential helper can indefinitely block authority refresh and handoff progress.
  - suggestion: Give src/garden/git_coordination.py:_run and _push one bounded subprocess abstraction with noninteractive authentication, descendant cleanup, and a total operation deadline. Treat an interrupted push as ambiguous and resolve its existing operation ID before execution. Add controlled stalled-fetch, stalled-push, and accepted-push/lost-reply tests that assert bounded return and retained obligations.

## Medium

- **Coordination history growth** — Every Git refresh walks and decodes the entire state history even when its head is unchanged, while each transaction retains an expanding operations table.
  - suggestion: In GitStateStore._fetch/_validate_history, cache validated immutable commit identities and validate only descendants of the last verified head while retaining rewrite detection. Batch Git object reads and define a retention/checkpoint strategy that preserves replay resolution. Add deterministic command-count tests for unchanged heads and one-commit advancement; measure larger histories separately under the stress policy.
- **Integration test architecture** — The headline two-user recovery and phase-owner journeys still inject the obsolete HTTP/SQLite coordinator rather than exercising the configured Git client.
  - suggestion: Port tests/test_multiplayer_workflow.py:93 and :204 to independent Git-backed installations created through supported configuration. Preserve competing-owner, restart, partition, late-result, and successful-handoff assertions through actual scheduler entry points. Keep obsolete-service tests explicitly labeled as legacy compatibility coverage rather than multiplayer release acceptance.
