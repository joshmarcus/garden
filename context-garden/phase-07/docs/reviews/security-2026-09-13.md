# security review of context-garden/phase-07

**Persona:** security · **Score:** 7/10 · 2026-09-13T16:42:33+00:00

Close with follow-ups. Phase 07 materially strengthens repository identity, exact-head validation, human authority, and recovery boundaries. I found two medium-severity gaps: stale approved-tool files survive mapping removal, and auxiliary CLI paths bypass scoped credential selection. This assessment uses source, test inspection, supplied PR evidence, and two in-memory probes; it does not establish private-environment deployment or end-to-end enterprise acceptance. The walkthrough directory was inaccessible, so I make no captured-UI claims. No files were modified or committed.

## Reaction

I would close Phase 07 with two focused security follow-ups. My confidence comes from several concrete boundaries in the implementation, rather than the number of completed tasks. This phase brings enterprise repository access, reusable remote machines, and canonical checkouts into a tool that executes model-directed code. Those capabilities make mistakes more consequential: a wrong identity can reach another repository, a stale result can authorize the wrong revision, and an overenthusiastic recovery operation can destroy somebody's work. I wanted to see those decisions anchored in controller-owned facts.

The repository routing work gives me substantial reassurance. Reading the scheduler's construction of source-control clients, I found explicit product routes and a deliberate switch away from ambient gh authentication when scoped transport settings apply. The REST path rejects redirects, and endpoint validation checks the configured authority. Those are useful protections because a credential boundary needs to survive the actual request, not merely appear in configuration documentation. The exact-head validation work follows the same principle. The supplied validation report distinguishes a result for the current commit from an old green result, and the tests address malformed, missing, stale, and mismatched evidence. I value that much more than a reassuring status label.

Following the credential path beyond the scheduler changed my assessment. The friction command and product-specific doctor checks instantiate GitHub directly with use_gh still enabled. That constructor stores the scoped token but does not force the CLI to use it. My in-memory probe supplied a synthetic gh executable, omitted the named token, and observed an available client returning the mocked ambient identity without an explicit subprocess environment. No real service was contacted. The main scheduler has already solved this case, which makes the remaining inconsistency particularly avoidable. A diagnostic command should test the authority the product will use; otherwise it gives the operator confidence in a configuration that may fail closed during real scheduling. Friction collection also performs reads under that unintended authority.

The approved-tool file feature has a similarly specific lifecycle gap. I like the named mappings, destination checks, and restrictive permissions. They make access reviewable and avoid copying an entire operator home. But the worker home persists, while installation processes only the mappings that still exist. Removing the final mapping returns before any filesystem operation; changing a destination leaves the old destination behind. The existing revocation test deletes the source file while retaining its mapping, so it proves a narrower case than withdrawing the mapping itself. A worker can therefore retain access to an old credential after the operator believes that capability has been removed. I would reconcile previously managed destinations at launch, preserving unrelated caches. This would remove Garden's stale copies; it would not pretend to revoke a credential that a previously authorized process deliberately copied elsewhere.

On prompt injection, I was reassured to find that ordinary public commenters do not automatically become worker instructions. GitHub feedback checks trusted authors and separately requires explicit bot trust. That does not make a trusted bot's prose inherently safe, especially when an integration relays other people's text, but it gives the owner an actual authority decision. I also checked an apparent shell hazard in the SSH brief transport: the brief is embedded in a quoted heredoc, and the launcher rejects its delimiter in the supplied text. I did not turn that initial suspicion into a finding once I saw the guard. Security review should reward a boundary that is present, even when the surrounding mechanism initially looks uncomfortable.

Recovery and deletion deserve the same discipline. Canonical checkout preflight refuses dirty work and unexpected branches, and it rejects the controller checkout and symlink aliases. Branch cleanup compares recorded heads and retains the local recovery copy when remote deletion fails. The CG-405 recovery account is also candid about a correction that initially failed to reach merged delivery. That is a material evidence problem, but the supplied closeout records its recovered delivery and independent validation. I would reuse CG-659 for the broader reconciliation issue rather than file a duplicate or demand another author round solely because commit identities changed.

My evidence has limits. I could not open the supplied walkthrough directory because access was denied, so I cannot quote the pages or judge whether their controls communicate these boundaries well. I inspected source and tests and ran only read-only, mocked probes; I did not run the full suite or a private enterprise pilot. The enterprise validation report itself carefully separates synthetic regression coverage and a local tmux probe from remote execution and deployment. I want that distinction preserved in the retrospective. The owner has explicitly deferred evidence-storage work and rejected the shared-coordinator direction; neither decision becomes a Phase 07 defect simply because broader infrastructure would make some security arguments easier. My next investment would be consistency across existing entry points and revocation lifecycles, followed by explicitly authorized environment verification—not reopening deferred architecture or treating merged source as permission to widen access.

## Medium

- **Tool configuration revocation** — Removing or changing an approved config-file mapping leaves the previously installed file available in the persistent worker HOME.
  - suggestion: In src/garden/runner/base.py:276 and the equivalent SSH installation path, track previously managed destinations and safely remove obsolete copies before launching another run, including when the mapping becomes empty. The crossed boundary is current operator authorization versus retained worker capability: a later worker or branch test can read a still-valid credential after its mapping was removed. Preserve unrelated caches and add regression coverage for mapping deletion, destination changes, and an empty allowlist across supported transports.
- **Scoped CLI credentials** — The friction and doctor CLI paths can use ambient gh authentication even when the product explicitly names a scoped token source.
  - suggestion: Route src/garden/cli/planning.py:254 and src/garden/cli/diagnostics.py:491 through the same scoped client construction used by the scheduler, or enforce explicit credential selection centrally in GitHub. The crossed boundary is product-specific authority versus the operator's ambient identity: with a missing or revoked scoped token and an authenticated gh executable, friction collection can still read repository data and doctor can report successful authentication. Fail closed on missing scoped credentials and cover these CLI entry points with ambient gh present.
