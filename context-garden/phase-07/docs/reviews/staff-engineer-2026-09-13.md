## Reaction

I would close this phase with follow-ups, but I would not translate that decision into a claim that the private enterprise environment has been exercised. The owner’s closeout notes make that distinction explicit, and I appreciate it. Evidence planning, the private pilot and deployment verification have accepted scope boundaries. Reopening those decisions would create work without establishing a new defect. My confidence here concerns the delivered source and the supplied verification record. The walkthrough directory returned permission denied, so I cannot judge the captured pages or quote their rendered controls. I also did not rerun pytest or full CI during this read-only review.

What I welcome most is the effort to make authority explicit. Reading the source-control contract, I see provider operations separated from scheduler decisions about protected paths, stack ownership and merging. Reading the command-CI contract, I see an answer that must identify the requested commit and explicitly claim current evidence before it can pass. Those choices make enterprise integration understandable without requiring every adapter to become a second scheduler. The distinction between pending, absent and unavailable evidence also matters operationally: an author should not receive an implementation revision because an external service cannot answer a question.

The feedback composition module is another decision I would be glad to inherit. Review findings, CI findings and individual comments have separate contributions, and replacing one producer’s answer preserves the others. The code also treats an operator’s edited handoff as authoritative text instead of rebuilding it from an older review. That is a concrete reduction in maintenance risk. Losing one person’s decision when another asynchronous result arrives is difficult to diagnose because each individual component can appear to have worked correctly. Giving those contributions identities addresses the underlying problem.

The host-admission recovery changed my assessment in a positive direction. The closeout evidence explains that the original merge omitted a later correction, and current source contains the subsequent cancellation and release safeguards. I inspected the pattern of reading state under a lock, making a provider call, then rereading and checking the expected lease before committing the result. I would preserve that explicit ordering. It is tempting to shorten such code, but the intervening provider call is precisely where assumptions become stale. I would route delivery-reconciliation concerns into existing CG659 rather than file another version of the same problem.

The place where my confidence fell was canonical reconciliation. The surrounding design takes checkout ownership seriously: it rejects dirty trees and branch drift, records preparation ownership, and protects remote work through collection. Yet the local reconciliation command uses a shell timeout without explicit descendant cleanup. I ran a harmless probe that printed its child PID and slept. Reconciliation reported timeout after 1.0 second while the child was still alive; I then terminated that child. The scheduler’s exception path releases the lease and marks the run failed. That combination permits an old reconciliation process to overlap a replacement, despite the surrounding ownership machinery.

The existing timeout test illustrates the testing distinction I care about. It verifies that an exception occurs and a stale lease can be reclaimed. Those observations are useful, but they do not establish that reclaiming is safe. I want the test to prove that the previous owner can no longer mutate the checkout. This is a narrow behavioral repair, not a reason to restart the phase or design a new coordinator. It should precede reliance on the affected opt-in mode.

I have a related concern about controller-side command CI. Its result validation is careful, but its execution still occurs synchronously while the scheduler holds its controller lock. A timeout can therefore delay unrelated collection and operator actions. The output cap also applies only after all output has been buffered. These are separate responsiveness and memory-boundary problems, even though one well-scoped subprocess facility could help both. I would carry forward the product’s existing detached-work approach and exact-source identities rather than introduce another scheduling authority.

On avoidable review rounds, I support the direction shown by CG443, CG449 and CG450: preserve substantive findings, distinguish infrastructure limitations from unmet outcomes, and give revision authors complete feedback. The supplied descriptions do not let me measure how many rounds were wasted. They do show why rigid metadata cannot substitute for reading evidence: CG628 contains a detailed hosted comparison alongside generated criterion entries saying no evidence was given. I would reconcile those representations before demanding another author run, while retaining actual CI failures and contradictory provenance as blockers. Existing CG661 remains the appropriate home for broad-label repeated-finding classification.

As a future maintainer, I see useful simplification here, particularly in explicit feedback ownership and the audit’s refusal to delete recovery machinery merely because it is complicated. My next investment would be in a few behavioral boundaries: no surviving writer after lease release, no slow adapter monopolizing the controller, and no supposedly bounded response consuming unbounded memory. Those repairs would make the phase’s architectural promises more dependable without reopening accepted deferrals.

## High

- **Canonical checkout recovery** — Local reconciliation can leave a child running after timeout while the scheduler releases its checkout lease, permitting overlapping mutation during a retry.
  - suggestion: In src/garden/canonical.py:114, supervise reconciliation descendants and confirm termination before returning a timeout; in Scheduler.prepare_canonical_run, retain ownership if cleanup is uncertain. Extend tests/test_canonical.py beyond exception and lease-reuse assertions to prove a timed-out child cannot continue writing after replacement admission. A read-only probe confirmed reconciliation returned after 1.0 second while its harmless child remained alive; the probe explicitly terminated that child.

## Medium

- **Controller responsiveness** — Command CI queries execute synchronously under the controller lock, so an unavailable adapter can block unrelated scheduler work and locked operator actions for its full timeout on each distinct head.
  - suggestion: Move command observations outside the controller critical section using the existing detached-work approach, then consume results bound to provider policy and exact SHA. src/garden/ci_status.py:269 defaults to a 120-second query budget and permits 3600 seconds; tick-level caching does not bound a pass across distinct heads. Add a small deterministic test proving a stalled adapter does not delay unrelated result collection or a locked operator action, and that late results cannot qualify a changed head.
- **CI adapter resource bounds** — The command-CI output limit is checked only after subprocess.run has buffered all stdout and stderr, so it does not bound controller memory consumption.
  - suggestion: Replace capture_output buffering in src/garden/ci_status.py:271 with bounded stream consumption for both channels, terminating owned processes when the limit is exceeded and returning an unavailable or malformed result. Reuse the process-supervision primitive where appropriate. Add bounded producer tests for excess stdout and stderr; the existing oversized-JSON test proves rejection after allocation rather than a resource limit.
