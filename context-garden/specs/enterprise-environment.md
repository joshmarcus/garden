# Enterprise environment architecture

Context-garden fits into an enterprise development environment through explicit boundaries for source, identity, execution, evidence, and authority. Shared context contains portable policy and logical names. Deployment-specific endpoints, identities, and credentials stay in protected configuration and are resolved only by the component that needs them.

Enterprise integration is a set of narrow contracts around the existing task, run, review, and merge lifecycle. A product keeps its repository, base branch, checks, ownership, and policy independent of every other product. Shareable configuration names logical providers, worker pools, tools, and policies. Local configuration or a secret service resolves physical endpoints and credentials at the last responsible boundary. Effective configuration diagnostics explain which layer supplied a value without printing the value when it is sensitive. Unknown settings and incompatible combinations fail with an actionable error; they never select a broader identity or weaker execution mode as a fallback. CG-349 and CG-350 establish the layered configuration and provenance model that these integrations extend.

## Source control and change identity

Every repository operation carries an explicit product identity: provider, web endpoint, API endpoint, repository, base branch, and proposed source revision. Discovery, links, authentication checks, pull-request reads and writes, reviews, status checks, rebases, and merges must resolve through that identity rather than an ambient command-line login. CG-395 and CG-447 provide explicit GitHub Enterprise host and repository normalization, while CG-432 keeps onboarding metadata transport-independent. A provider adapter exposes common repository and change-request operations without forcing other services into GitHub-shaped configuration. CG-515 owns the provider interface and scoped certificate/proxy contract.

Connection policy may include an enterprise certificate-authority bundle and outbound proxy. Those settings are scoped by endpoint and operation, passed through supported client interfaces, and never implemented by disabling certificate verification. Redirects cannot move scoped authorization to a different authority. Authentication failure, unavailable service, and invalid certificate or proxy configuration remain distinct diagnostics.

Change evidence is bound to the exact proposed head or an explicitly identified merge tree. CG-396 and CG-467 define pluggable exact-source validation, including installations without GitHub Actions. CG-475 refreshes conflicts, reviews, check runs, and status contexts; CG-464 preserves the clean approved head while still requiring a fresh conflict check and atomic head guard. A prior green revision, an incomplete job set, or an inaccessible result is not a pass.

Branch publication has one declared owner. CG-397 protects externally managed stacks and configured sensitive paths, and CG-406 fences canonical checkouts. Garden may verify an externally managed branch without racing its owner through a force-push or retarget. Review, merge, deployment, and phase closure are separate authorities. A credential that can perform an operation does not grant product approval to perform it.

## Workspaces, runners, and managed hosts

The workspace strategy belongs to the product. Independent worktrees remain the normal isolated strategy. A canonical or managed checkout uses the exclusive lease, dirty-workspace refusal, source checks, reconciliation hook, and recovery behavior established by CG-406. Different aliases that resolve to the same physical workspace share the same exclusion boundary. Recreating a checkout invalidates preparation state tied to the old workspace identity, as specified by CG-508. Setup and per-run reconciliation are separate: setup prepares an environment, while reconciliation restores the source and filesystem into the state required for one run.

Runner adapters are registered only through trusted operator configuration and must declare a compatible interface and capabilities, following CG-415. They do not opt out of admission, environment scrubbing, source fences, result validation, or review policy. CG-404 supplies a provider-neutral command-backed lifecycle and transport contract, including explicit argument, input, output, exit, timeout, cancellation, readiness, reuse, and retirement behavior. CG-345, CG-346, CG-347, and CG-348 apply the same lifecycle principles to managed compute.

Long operations have durable logical identities and resumable states. Requested, provisioning, verifying, ready, busy, draining, failed, and retired are distinct. Bounded read-only readiness probes verify the intended checkout, runtime, tools, permission, and capacity without formatting or mutating source. The scheduler prefers a compatible ready host before acquiring another. Pool size, cost authority, and absolute expiry survive retries and controller restarts. Failure to provision or become ready is an environment failure and does not consume an author's implementation attempt.

Shareable records use logical worker aliases. Physical connection information is resolved only by the lifecycle or transport boundary and is excluded from task files, briefs, notifications, and public evidence under CG-399. A deployment may use pull-based workers, controller-originated managed access, or a direct transport; it does not require worker-to-worker reachability or unrestricted inbound access. Active work drains through its lease and result protocol before release whenever authority remains valid.

## Identity, tools, and execution boundaries

Worker authority is assembled per run from named capabilities. CG-401 copies selected tool configuration into scrubbed local and remote environments with safe paths and restrictive permissions. CG-516 defines workload identity resolution as a separate contract for short-lived or renewable credentials: the resolver receives a logical reference, operation, audience, and run identity; it returns only the least authority required for the bounded operation; and it records issuer and expiry metadata without recording the credential. Human and automation identities remain distinguishable in audit records.

No worker receives an operator's whole profile. Environment variables and configuration files are allowlisted. Missing membership, expired credentials, unavailable sandbox support, or an unrecognized identity provider fail closed. Revocation must affect new operations promptly and produce a useful environment diagnosis rather than an implementation revision.

Filesystem and network policy are part of execution authority, not prompt advice. Worker code may write its authorized checkout and per-run work area while scheduler state, approvals, credentials, sibling results, and unrelated products stay outside the writable boundary. Network access is limited to named destinations needed by the run. Platform capability checks may select a documented safe enforcement mechanism, but a configuration flag cannot silently discard deny paths or run without the required sandbox. Planner and synchronous kickoff execution need the same enforced boundary because planning documents are untrusted inputs; CG-245's scrubbed scratch execution is the foundation, while CG-518 owns OS-level enforcement and rejection of bypass permission modes.

Worker credentials authenticate only worker protocol operations. Operator controls require their own authentication and must not become reachable merely because the worker API is reachable. CG-216 supplies authenticated claim, heartbeat, and finish routes; CG-517 separates those routes from authenticated operator access on worker-reachable networks.

Tool output and generated artifacts are data. They cannot add tools, widen policy, or create executable configuration. HTML, SVG, and other active formats render through a sandboxed origin or response policy with restrictive content headers; unsupported formats download as inert files. CG-318 supplies the design and capture surface, with CG-519 applying this rule consistently to every raw response.

## Validation, admission, and recovery

The CI status contract accepts repository identity and requested revision and returns normalized state plus original provider identity, tested head or merge tree, required jobs, run attempts, and controlled diagnostic references. Status retrieval and failure-log analysis remain separate. Missing, partial, stale, inaccessible, and failed evidence keep their distinct meanings. Infrastructure failures are diagnosed before bounded retry; implementation failures return exact-source feedback, and an earlier failed result remains in history after a later pass.

Admission combines controller-wide limits with the execution host or pool's capacity. CG-361, CG-365, CG-405, and CG-413 cover resource leases, host-local routing, and product-specific weights and timeouts. CPU, memory, disk, concurrency, and heavy-check limits coordinate across processes that share the constrained resource. Capacity reservation and release survive crashes; reconnecting workers cannot create a second authoritative generation.

CG-428, CG-457, CG-466, CG-491, CG-495, CG-501, and CG-506 define the remote recovery chain: live heartbeats, queue and execution-time accounting, idempotent claim recovery, active-run selection, transport diagnosis, fenced result return, and durable transcripts. A terminal authority or absolute deadline stops surviving descendants. Partial output remains attached to its attempt. Restart and retry preserve accepted work without claiming exactly-once execution where the transport cannot provide it.

## Review and governance

Trusted reviewer identities are configured per product. Findings retain author, revision, criterion, severity, resolution state, and immutable original verdict. CG-450 and CG-474 preserve full asynchronous feedback across handoffs; CG-443 and CG-462 keep advisory limitations and proportionate evidence from causing mechanical revision loops. Genuine defects, applicable failed checks, explicit rejection, and contradictory source evidence remain blockers.

Organization-specific pull-request templates and protected paths are product policy. Automated merging is opt-in and follows the configured review threshold, exact-head checks, fresh conflict check, and atomic head guard. Human-only workflows retain the same evidence and handoff identities without granting Garden merge authority. Externally completed work uses the verified completion and provenance paths in CG-362 and CG-476. Completion records distinguish implementation, approval, merge, release, deployment, and deployed-boundary verification.

## Confidentiality, evidence, and notifications

Task briefs, prompts, logs, reports, examples, and notification payloads are classified by destination. Shared specifications use synthetic names and values. Sensitive connection data is resolved at runtime. Redaction applies before persistence and transmission and operates across streamed chunk boundaries. It records that redaction occurred without leaking the removed value.

CG-506 provides attempt-scoped transcript transfer, integrity metadata, partial-attempt preservation, and authorized retrieval. Evidence storage may remain local or use an access-controlled adapter, but the record keeps stable task, run, attempt, source, check, artifact, and verdict identities. Retention and deletion policy applies independently to raw logs, transcripts, rendered artifacts, and sanitized manifests. CG-402 defines immutable evidence export and remains subject to its explicit policy hold; ordinary enterprise integration must not bypass that decision by publishing private material elsewhere.

Notification delivery uses a logical destination reference from trusted configuration. CG-398 demonstrates safe structured notification construction and human-gated operation. CG-520 defines a general adapter that receives a typed event rather than a shell string, enforces bounded delivery and retry, and filters fields for the destination. Worker-authored text is never interpolated into an executable command. Repeated unchanged failures are coalesced, while delivery failure remains visible without corrupting task state.

Operator views distinguish queued work, active execution, environment holds, review findings, and intentional deferrals. CG-480, CG-499, and CG-501 provide the ownership and worker-health vocabulary. Cost and progress surfaces name their cohort, time window, source, and completeness; unknown price remains unknown. A missed target remains measured history even when an authorized person later accepts the result.

## Verification contract

Enterprise capabilities are verified with disposable repositories, synthetic endpoints, provider fakes, and offline workers. Coverage includes endpoint selection, scoped authentication failure, certificate and proxy errors, branch changes, stale heads, partial CI jobs, unavailable logs, dirty and recreated workspaces, duplicate acquisition, interrupted readiness, resource saturation, controller and worker restart, expired authority, descendant termination, redaction across chunks, safe active-document preview, notification failure, and durable partial results. Tests use generic identities and never contact or describe private infrastructure.

Live infrastructure exercises are optional and require their own authority for access, cost, and mutation. Their absence does not convert a deterministic result into a failure, and their presence does not replace exact-source verification, security boundaries, or governance approval.
